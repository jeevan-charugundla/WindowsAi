# V1.5 Visual Teacher

V1.5 adds visual guidance without computer control.

## Architecture

1. The user explicitly chooses **Guide Me** and asks a visual question.
2. `ScreenCaptureService` captures the primary display once in memory.
3. The desktop sends the image, question, and captured physical pixel dimensions to `POST /api/ai/visual-teacher`.
4. The backend asks Groq Vision for one JSON target.
5. The backend validates the instruction, rectangle, confidence, and screenshot bounds.
6. The desktop displays a passive WPF overlay with a highlight and instruction.

## Response contract

```json
{
  "instruction": "Click the Settings icon",
  "target": {
    "x": 142,
    "y": 80,
    "width": 32,
    "height": 32
  },
  "label": "Settings",
  "confidence": 0.91
}
```

The provider's internal response uses integer normalized coordinates from 0 to 1000 based on the original image. The backend validates that normalized rectangle first, including a conservative maximum dimension for a single UI element so a whole-screen box is rejected, then converts it to integer physical pixels using the actual PNG width and height. The public response returns physical `target` coordinates plus `normalizedTarget` for development diagnostics. The request also includes `screenWidth` and `screenHeight`; the backend performs a second physical bounds check and rejects rectangles where `x` or `y` is outside the image or where `x + width` or `y + height` exceeds the image bounds.

`ScreenCaptureService` returns the bitmap's own width and height as metadata, so the dimensions used for conversion are the dimensions of the encoded PNG.

The overlay converts physical pixels to WPF device-independent units using the primary monitor DPI from `GetDpiForWindow` after the overlay is loaded. This keeps the screenshot and overlay in the same coordinate space when Windows display scaling is enabled.

In DEBUG builds, setting `WINDOWS_AI_COMPANION_VISUAL_DEBUG=1` shows the label, confidence, normalized target, and physical target. It is disabled by default and does not include screenshot data.

## Confidence handling

- `>= 0.75`: normal guidance.
- `0.50` to `< 0.75`: the instruction is marked as uncertain.
- `< 0.50`: the backend rejects the target and no overlay is rendered.

Model confidence is only a self-reported estimate, not an independently verified correctness score. The UI labels it as `AI confidence` and does not treat 100% as a guarantee.

When the requested element is not visible or cannot be identified reliably, the provider may return `target: null`, an empty label, and confidence `0`. The backend returns the friendly instruction `I couldn't confidently locate that on the current screen.` and the desktop adds it to chat without creating an overlay.

## Safety boundary

The overlay only draws a visual target and instruction. It does not move the mouse, click, type, invoke UI Automation, launch processes, execute commands, or continuously capture the screen. The screenshot is held in memory for the explicit request and is not stored in the conversation or on disk. The instruction bubble is placed above the target when possible, otherwise below or clamped within the screen bounds.

V2 can build an explicit permissioned action layer on top of this validated guidance, but V1.5 intentionally stops at visual teaching.
